# 协作策略路由（多智能体协作方式选择）

> 沉淀自 2026-10-06 调研（Stanford CS224g、AutoGen 官方文档、多智能体编排指南等多源交叉验证）。用途：主调控者决定"这个任务用哪种协作方式组织子任务"，可按任务类型切换，不绑定单一策略。

## 一、两大体系（正交，可共存）

**A. 推派体系（push，主管主导）** —— 主管拆解→委派→验证→汇总：
| 模式 | 一句话 | 适合 |
|---|---|---|
| Supervisor / Orchestrator-Worker | 主管拆解→委派→验证→汇总 | 可分解的复杂任务（最主流） |
| Hierarchical 层级 | 战略→规划→执行 多层嵌套主管 | 10+ 专家、超大型项目 |
| Pipeline 流水线 | A→B→C 固定工序单向 | SOP 明确、工业化批量 |
| Fan-Out/Fan-In 扇出扇入 | 1→N 独立并行→合并 | 独立子任务、best-of-N |
| Debate 辩论 | 多方互批收敛（减幻觉） | 高利害正确性、合规、质控 |
| Voting 投票 | N 次独立跑→聚合 | 以算力换置信度（一般任务不划算） |
| Reflection 反思 | 自生成→自批判→修改 | 单 agent 内质量提升 |
| Specialist Routing 专家路由 | 路由器→1/N 专家 | 多类查询分流 |
| Adversarial 对抗评估 | 构造失败用例暴露弱点 | 评估 agent 本身 |

**B. 拉取体系（pull，协作者自取）** —— 任务放共享空间，协作者按能力认领：
| 模式 | 机制 | 适合 |
|---|---|---|
| Blackboard 黑板 | 共享黑板读写；可配 supervisor 定激活顺序（1970s AI 研究起源） | agents 数/顺序不确定（如监控群） |
| Kanban Pull 看板拉取 | 任务队列 + **按能力认领**；原子认领防重复；生命周期 available→claimed→in_progress→review→done | 任务多而独立（渠道扫描） |
| Contract Net 合同网 CNP | 发布→**投标**→中标→执行→交付；全 peer + 共识投票 + 审计日志 | 无中央权威、需可审计 |

**C. 群聊类（AutoGen 官方 4 种 Team）**：RoundRobin（轮流）/ Selector（动态选下一个发言者）/ Swarm（handoff 转交）/ GraphFlow——本质是"下一个谁说话"的选择策略，可嵌套进 A/B。

## 二、能共存吗？——能，而且是常态

推派和拉取是**正交的两个轴**，不是二选一：
- 主管管规划（定计划、拆任务、验收），黑板/看板管分发（工人按能力认领）——Supervisor + Blackboard 混合是成熟做法
- 看板里嵌验证：认领的工人做完→review 状态→独立评审通过才 done
- 监控类任务尤其适合拉取：每个扫描 agent 认领一个渠道，无中央规划（如 50 个研究 agent 探索 50 个假设）

## 三、本项目/本监控仓的推荐路由

```
简单任务（问答/单步）        → 单 Agent 直做（不派活）
调研/盘点（多源并行）        → 主管-工人 + 扇出扇入 + 独立验证（当前主力）
生产流水线（出片/批量内容）   → Pipeline 顺序工序 + 阶段门禁
高利害决策（定稿/合规/选型）  → Debate / maker-checker（生成→验证→通过才继续）
质量复查（SOP/产物评估）      → 对抗评估 + 反思
监控扫描（定时）             → 拉取体系（各渠道认领）+ 主管汇总验证 ← 引入建议
超大项目（10+ 专家）         → Hierarchical 层级
```

**切换成本低**：决策层（主调控者）不变，变的只是子任务怎么组织；策略写在执行计划里即可。
